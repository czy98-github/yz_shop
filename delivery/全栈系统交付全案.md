## 一、Phase 1 · 需求与平台选型

> 完整产出：`docs/需求与平台选型报告_特色菜订餐小程序.md`（55 KB）

### 1.1 选型结论

**唯一主推荐端组合**：微信小程序（C 端，uni-app + JS）＋ Web 后台管理（B 端，Vue3 + Element Plus）
**唯一首选开源底座**：`guchengwuyue/yshop-drink`（意象点餐），匹配度 **93/100**

| 排名 | 仓库 | 分数 | 一句话结论 |
|---|---|---|---|

| 2 | siam1026/siam-server | 77 | Apache-2.0，但 SpringBoot2.3.3→3 + Vue2→3 双升级 |
| 3 | fushengqian/fuintCatering | 69 | 技术契合高，但**商用需付费购买源码授权**，不推荐 |
| 4 | woniudiancang/bee | 56 | 4588 stars 但**只有原生小程序、无后端**；实为木兰宽松许可证 v2，非禁止商用 |

| 6~10 | 其余 5 个 | 45~18 | 分别为 4 年未更新、无 LICENSE、纯后端、Node 技术栈、已归档 |

### 1.2 为什么选 yshop-drink（四条硬证据链）

1. **技术栈零大版本迁移**：Spring Boot 3.2.2 + Java 17 + 管理端 Vue 3.4.21 + Element Plus 2.6.1 + Vite + 小程序 uni-app 2.x + MySQL dump 8.0.27 → 目标栈四要素全命中
2. **许可证最友好**：MIT（根目录 LICENSE，Copyright (c) 2023 yshop），允许商用 + 闭源二次开发
3. **功能闭环完整可验证**：菜品 + 分类 + 多规格、购物车、下单、订单状态机、后台 6 域页面、订单导出开箱即用
4. **活跃可运行**：最后 push 2026-10-15（距今 15 天）、README 含完整启动步骤、15.45 MB 完整 SQL dump、knife4j 4.3.0

### 1.3 平台选型逻辑

C 端 = 微信小程序（uni-app + JS）；B 端 = Web 后台（Vue3 + Element Plus）。**不规划 App / iOS / 鸿蒙 / 桌面端**。

判据：集团内部低频工作日场景装 App 会被卸载；B 端长时间桌面操作命中 Web；技术栈同构优先，不引入 Flutter/RN/原生。

## 三、Phase 1 · 技术研发方案

> 完整产出：`/Users/tristan/yshop-analysis/技术研发方案_yshop-drink差距分析与部署验证.md`（约 56 KB）

### 3.1 架构模式

**前后端分离单体**（判据：多端共用一套 API 的标准形态，日活千级禁止微服务）。

```
微信小程序（uni-app 2.x + Vue3 + JS）
        │ /app-api/*
        ▼
Spring Boot 3.2.2 单体（yshop-server，13 模块）
   ├─ yshop-framework（14 个 starter：web/security/excel/mybatis/redis/quartz/...）
   ├─ yshop-module-mall（product / order / store / member / pay / marketing）
   ├─ yshop-module-system（用户/角色/菜单/字典/租户）
   ├─ yshop-module-infra（文件/配置/代码生成/任务）
   └─ yshop-module-mp、yshop-module-score（保留不挂菜单）
        │
   ┌────┴────┬──────────┬────────────┐
MySQL 8.4  Redis 8.x    对象存储     日志/监控
(主从动态)  (Redisson)   OSS/CDN
```

### 3.2 34 项差距对照摘要

| 类别 | 结论 |
|---|---|
| **四项硬性目标栈** | 后端（Java17+SB3.2.2）**零改造**；管理端（Vue3.4.21）**零改造**；数据库（8.0.27→8.4）**0.5 人日**；小程序端（uni-app2.0 JS）**零改造** → 合计 **19.5~26.5 人日** |
| **业务功能缺口** | 菜品展示 ✅、下单 ✅、订单流转 ✅（口径需重定义）、后台管理 ✅（菜单重排 2 人日）、**订单导出 ⚠️ 仅 .xls 需加 CSV（0.5~1）**、**统计数据 ❌ 完全缺失（3~4）** |
| **部署运维缺口** | docker-compose 4 处失效、端口双轨、上游凭据残留、运维基线缺失 → **4.0 人日** |
| **合计** | **28.5~37.5 人日**（含 20% 缓冲 **34~45 人日**） |

### 3.3 MySQL 8.4 兼容（已实测定论）

**原始 SQL 是 MySQL 8.0.27 方言，不是 PostgreSQL**（Linguist 误判；SQL 头明写 `Source Server Type: MySQL / Version: 80027`；全库 `COMMENT ON=0`、`jsonb=0`、`AUTO_INCREMENT=163`、`ENGINE=InnoDB×94`）。

**主控实测结论**：原始 SQL **直接导入 MySQL 8.4.11 成功，94 张表零错误**（研发师此前担心的 `utf8mb3` 别名移除问题，在 8.4.11 上未触发导入失败）。

但仍有一项**真实业务影响**（主控已量化）：

| 项 | 实测值 |
|---|---|
| `utf8mb3_general_ci` 表 | **28 / 94**（含 `yshop_store_order`、`yshop_store_product`、`yshop_user`、`yshop_store_order_status` 等 17 张核心业务表） |
| 受影响列 | `yshop_store_order.out_trade_no`（退款单号）、`shop_name`（店铺名）、`yshop_express.code/name`、各审计列 |
| 业务后果 | **不支持 emoji 与生僻字**（「辣子鸡🐔」「Ángel」会报错或截断） |

→ 处置：批量 `ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`，**上线前必须完成**。

### 3.4 实测踩坑记录（价值最高的部分）

| 坑 | 现象 | 正解 |
|---|---|---|
| **JDK 版本** | pom 写 `<java.version>17</java.version>`，但编译日志是 `javac [release 21]`，用 JDK 17 编译直接失败「不支持发行版本 21」 | **必须用 JDK 21** |
| **MySQL 安装** | Homebrew 已停止为 Intel x86_64 构建 bottle；USTC 镜像有 JS 验证墙（返回 877 字节 HTML） | 用 `cdn.mysql.com/Downloads/MySQL-8.4/mysql-8.4.11-macos15-x86_64.tar.gz` 官方包（171 MB） |
| **Redis 安装** | 无官方二进制包 | 源码编译（`make`，4分36秒） |
| **前端包管理器** | `npm install` **失败 ERESOLVE**：`vue@3.4.21` 与 `@form-create/designer@3.5.0` 的 peer `vue@^3.5` 冲突 | **必须 `pnpm install --frozen-lockfile`**（lockfile 锁的是 `3.1.5`，兼容 3.4.21） |
| **依赖漂移风险** | package.json 中带 `^` 的直接依赖共 **43 个**，任何 npm 安装都会随时间漂移 | 以 lockfile 为唯一事实来源，升级走 `pnpm update <pkg>` 并提交 lockfile |
| **上游凭据残留** | `mp_account` 种子含真实 appid+secret、钉钉/快递鸟/腾讯LBS/百度 AK、`yshop.file-path: /Users/hupeng/drink/file/`（作者本机绝对路径） | 上线前逐项清理，密钥一律环境变量注入 |
| **许可冲突** | 根目录 MIT LICENSE，但几乎所有 Java 源文件头写「未经购买不得使用 / 禁止上传到 github 等开源平台」 | **需法务书面结论后方可商用**（见第十一章） |

## 四、Phase 2 · 测试保障方案

> 完整产出：`测试保障方案_特色菜订餐小程序.md`（46 KB）

### 4.1 质量门禁结论：❌ **不通过，禁止放行**

8 项门禁：1 项通过（性能）、4 项不通过、3 项未完成。**P0 bug = 1 → 存在即禁止上线。**

### 4.2 实测覆盖

50 例已实际发 HTTP 请求验证：真实通过 **33**、真实缺陷 **6**、需凭证阻塞 **4**、连带阻塞 **7**。异常流 22 例 ≥ 正常流一半。

### 4.3 性能实测（有余量）

- 商品列表 P95 ≈ 49 ms
- 后台订单分页 P95 ≈ 83 ms
- 主控实算峰值 QPS < 1（2000 人在册、30% 集中在 30 分钟、3× 尖峰），运维基线容量目标 36 QPS → **余量 2~70 倍**

### 4.4 安全侧亮点（8 例全过）

管理端无 token / 伪造 token / 用户端无 token 均拒绝；**admin token 访问 app-api 被拒**、**用户端 token 访问 admin-api 被拒**（垂直越权防护有效）；订单详情按 uid 过滤。

### 4.5 放行最小集（6 项）

① 修 DEF-001（P0 密码明文） ② 补 CSV 导出 ③ 修 DEF-002（响应头丢失） ④ 修 DEF-005/006 ⑤ **提供微信 appid/secret** ⑥ 补兼容矩阵 + 并发压测

### 6.1 监控告警（三层，含数值阈值）

| 层 | 关键指标与阈值 |
|---|---|
| 基础设施 | CPU / 内存 / 磁盘 / 网络；连接池 Druid `max-active=20` 使用率 >80% 告警 |
| 中间件 | MySQL 主从延迟 >1s、慢 SQL（阈值 100ms）、Redis 连接与内存、Redisson 连接池（实测 24 连接） |
| 应用 | JVM 老年代 / GC 停顿、**下单接口 P95 ≤800ms**、读接口 P95 ≤300ms、5xx 错误率 |
| 业务 | 订单创建成功率、支付成功率、下单→出餐耗时、**库存告罄菜品数**、弃单率、取餐码核销率 |

### 6.2 应急预案（8 个场景）

MySQL 主库故障 / Redis 故障与缓存击穿 / 接口 5xx 突增 / **下单失败但支付成功（幂等与对账）** / 库存超卖 / 微信支付回调丢失 / Quartz 任务堆积 / 磁盘写满。

每条含：故障现象 → 根因定位步骤 → 处置动作 → 回滚/降级 → 业务影响面。

### 6.3 对账与幂等

- `yshop_store_order_status` 流水表（实测 105+ 条）是对账主依据
- **支付回调必须幂等**（订单号 + 交易号双唯一索引）
- ⚠️ 主控实测发现：基座 `cancelOrder` **不写流水**（逻辑删除），因此「取消」在流水表中无痕 —— 对账设计必须补这一点

### 6.4 安全加固（对标等保三级）

边界防护（DMZ + WAF）、入侵防范、恶意代码防范、数据安全（密码 bcrypt 已核实 `$2a$10$`/`$2a$04$`）、备份恢复（MySQL 每日 02:00 mysqldump 保留 ≥7 天 + binlog）、剩余信息保护、访问控制。

### 8.3 下单接口的必填约束（集成时必须知道）

| 参数 | 约束 | 传错的后果 |

### 8.4 取消订单的实现语义（影响所有漏斗分析）

`AppStoreOrderServiceImpl.cancelOrder` 第 889 行执行 `storeOrderMapper.deleteById(order.getId())` —— **取消 = 逻辑删除（deleted=1），不改 status，也不写 `yshop_store_order_status` 流水**。

⚠️ **后果**：`yshop_store_order.status` 永远不会出现「已取消」态值；**弃单 / 取消 / 预排过期三类断点在 V1.0 完全无法区分**，运营只能看「总流失率」。这是必须补齐的数据缺口。
