## 一、背景

### 1.1 为什么做

集团各园区/办公点引入属地特色菜供应（如扬州港集团本地特色菜品），但当前订餐依赖"微信群接龙 + 食堂手工统计"的方式，存在三个明确痛点：

1. **统计口径失真**：群接龙无法准确区分订单归属与取餐人数，食堂备餐量依赖经验估算，缺餐与浪费并存；
2. **结算链路断裂**：员工餐补额度、实际消费、报销三者无法自动对齐，财务月底需人工比对台账；
3. **库存不可控**：特色菜（如限量狮子头、扬州炒饭）常出现"报的名多了做不出来"或"做多了卖不掉"，当日可售范围没有任何系统化管控手段。

因此需要一个**集团内部专用、无外部交易属性**的轻量订餐工具：员工在小程序自助选餐下单，餐饮部管理员在后台配置每日可售范围并处理订单，全链路订单数据可导出 CSV 用于备餐与财务对账。

### 1.2 需求依据（与上游结论一致性声明）

| 维度 | 结论 | 与选型一致性 |
|---|---|---|
| 目标用户 | 集团内部员工（在册 500~3000 人，按 2000 人在册测算），管理员为餐饮部管理员与档口员 | 未变更 |
| 端组合 | 微信小程序（C 端）+ Web 管理后台（B 端） | 与技术栈约束一致，未变更 |
| 核心场景 | 工作日午餐时段浏览当日菜品 → 加购 → 下单 → 到餐取餐 | 未变更 |
| 明确需求 | ①菜品展示 ②下单 ③订单状态流转 ④订单与统计数据 CSV 导出 | 未变更，全部覆盖 |
| 支付方式 | 集团内部结算，采用**员工餐补账户余额扣减**为主通道，预留微信支付通道（见 4.3 与 8.1 风险项 R-01） | 按团长授权口径落地方案 |

> ⚠️ 需团长确认项见第十二章「风险与待确认项」。若确认改为微信支付真实收款，工期需 +3~5 人日，详见 R-01。

## 二、目标

### 2.1 业务目标

| 编号 | 目标 | 目标值（上线后首个完整月，2026-03-01 ~ 2026-03-31） |
|---|---|---|
| BG-1 | 员工绑定率 | 在册员工完成工号绑定人数 ≥ 60%（2000 人在册 → ≥1200 人） |
| BG-2 | 订餐渗透率 | 周活跃下单员工 ≥ 35% 的在册员工（≥700 人/周） |
| BG-3 | 履约质量 | 周完成取餐订单数 ≥ 3000 单；平均取餐率 ≥ 90% |
| BG-4 | 运营提效 | 食堂当日备餐与结算不再依赖群接龙人工汇总，日报由系统 CSV 直接导出，用工时下降 ≥ 50% |
| BG-5 | 结算准确率 | 订单明细 CSV 与财务账目差异率 ≤ 0.5% |

### 2.2 北极星指标

**周完成取餐订单数（Weekly Picked-up Orders, WPO）**

- 口径：`t_order.status = 'COMPLETED'` 且 `completed_at` 落在统计周（周一 00:00:00 ~ 周日 23:59:59，服务器时区 Asia/Shanghai）内的订单条数。
- 理由：只有"扣款成功 + 实际被核销取餐"的订单才代表员工真实吃上了特色菜。单纯下单量会被"下单不取"和"测试单"污染；单纯核销量会被"先取餐后统计"污染。WPO 同时约束了前端转化（能否下单）与后端履约（能否供得上）。
- 数据来源：`t_order` 表（主）+ `t_order_item` 表（菜品维度拆解）+ 埋点 `order_complete` 事件（漏斗校验）。

### 2.3 成功度量（指标口径表）

| 指标 | 计算口径 | 目标值 | 数据来源 | 统计频率 |
|---|---|---|---|---|
| WPO（北极星） | 见上 | ≥3000 单/周（首月均值） | `t_order` | 每周 |
| 支付成功率 | `pay_success` 事件数 ÷ `order_submit` 事件数（按 order_no 去重） | ≥ 99% | 埋点 `order_submit` / `pay_success` | 每日 |
| 弃单率 | `CLOSED` 订单数 ÷ 提交订单总数（15 分钟超时关单口径） | ≤ 3% | `t_order` | 每日 |
| 取消率 | `CANCELLED` 订单数 ÷ 提交订单总数 | ≤ 3% | `t_order` | 每日 |
| 取餐率 | `COMPLETED` ÷ (`PAID`+`ACCEPTED`+`READY`+`COMPLETED`) | ≥ 90% | `t_order` | 每日 |
| 下单→取餐时长 P50 | `completed_at - paid_at` 中位数 | ≤ 45 分钟 | `t_order` | 每日 |
| 客单价 | 统计周期 `total_amount` 之和 ÷ 订单数 | ≤ 集团设定单餐上限 | `t_order` | 每日 |
| 菜品缺货率 | 发生"份数售罄"的菜品数 ÷ 当日在售菜品数 | ≤ 5% | `t_dish_daily.sold_qty / limit_qty` | 每日 |
| 余额不足支付失败占比 | `pay_fail(reason=BALANCE_INSUFFICIENT)` ÷ `pay_fail` 总数 | ≤ 5%（V1.1 优化目标） | `t_payment_txn` | 每周 |
| 绑定→首单转化率 | 首单员工数 ÷ 绑定员工数 | ≥ 70% | `t_employee` + `t_order` | 每周 |
| **固定菜品占比**（REQ-01 触发指标，v1.1 新增） | 取"连续 5 个工作日下单菜品组合完全相同"的用户数 ÷ 当期有下单记录的用户数。聚合口径：`yshop_store_order` JOIN `yshop_store_order_cart_info`，按 `uid` + 工作日（周一~周五自然日序列，剔除法定节假日）分组，取每个 uid 的连续 5 日滑动窗口，窗口内菜品集合完全一致则该 uid 计数一次 | **≥ 25%** 才启动 REQ-01 开发 | `yshop_store_order` + `yshop_store_order_cart_info` | V1.1 结束后复盘时（一次性） |

### 2.4 关键漏斗（各段埋点见第 8.4 节）

```
app_launch → dish_list_expose → dish_click → cart_add → order_submit → pay_success → order_complete
```

断点诊断规则：任一段相邻转化率低于设定阈值即触发优化任务。

| 漏斗段 | 健康阈值 | 低于阈值的归因与动作 |
|---|---|---|
| app_launch → dish_list_expose | ≥ 95% | 首页加载失败率高 → 优化首屏与图片 CDN |
| dish_list_expose → cart_add | ≥ 12% | 菜品吸引力/价格/图片问题 → 运营调整菜品与文案 |
| cart_add → order_submit | ≥ 60% | 结算页流失 → 检查余额校验时机、备注输入摩擦 |
| order_submit → pay_success | ≥ 99% | 扣款链路故障 → P0 线上问题，当日修复 |
| pay_success → order_complete | ≥ 90% | 备餐产能或取餐体验问题 → 检查备餐节奏、核销台效率 |

### 4.3 支付/扣款方案说明（团长指定方向的落地）

**方案对比与选型**

| 方案 | 资金流 | 资质与合规 | 实现与运维成本 | 适配本场景 | 结论 |
|---|---|---|---|---|---|
| A. 微信支付（小程序 JSAPI 支付） | 员工微信零钱/绑卡 → 集团对公账户 | 需微信支付商户号 + 小程序餐饮类目资质 + 食品经营许可证 | 支付 + 退款 + 对账三套链路；退款需人工审核 | 员工已有餐补，再走真实付款会重复报销 | V1.1 备选 |
| B. 微信小程序虚拟支付 | 虚拟币 → 结算 | 仅适用虚拟商品，实体餐饮商品不适用；iOS 端限制明显 | 中 | 品类不适配 | **不采用** |
| C. 员工餐补账户余额扣减（集团内部结算） | 内部额度，无真实资金流 | 无第三方支付资质门槛；内部额度调整需审计留痕 | 最低；无支付网关依赖、可离线兜底 | 餐补本就是集团发给员工的福利额度，扣额度=完成结算 | ✅ **V1.0 主通道** |

**落地设计**

1. **支付抽象层**：后端定义 `PayChannel` 策略接口，V1.0 实现 3 个通道：
   - `SUBSIDY_BALANCE`（默认，主通道）：扣减 `t_employee.subsidy_balance`，写 `t_payment_txn`（direction=DEDUCT）；
   - `MANUAL`（兜底）：管理员在后台标记"线下已收"，用于现金/统一结算场景，不扣余额；
   - `WECHAT_PAY`（V1.1 预留接口）：本期仅保留接口与配置位，不实现调用。
2. **扣款与订单的原子性**：订单先落 `PENDING_PAY`（并预占库存），扣款成功转 `PAID`；扣款失败订单保留在 `PENDING_PAY`，用户可重试，15 分钟未支付自动 `CLOSED` 并释放库存。
3. **退款语义**：退款 = 额度回冲（`t_payment_txn.direction = REFUND`）+ 库存释放 + 操作日志，三者同一事务。
4. **额度超发防护**：`t_employee.subsidy_balance` 扣减使用行级 `UPDATE ... WHERE id = ? AND subsidy_balance >= ?`，以受影响行数判定成败，杜绝并发透支。
5. **额度上限/单日限额**：单笔订单金额上限由集团配置（默认 ¥100），员工单日累计上限默认 ¥150，超限在结算页直接拦截（配置项 `order.amount_limit` / `order.daily_limit`）。

> ✅ **结论（团长已裁决，2026-10-30）**：以餐补余额扣减落地 V1.0，微信支付作为 V1.1 可插拔通道。这既满足"集团内部结算"的真实诉求，又规避了支付资质、退款对账等与核心价值无关的复杂度。技术侧对应编号 `T-01`（已定稿，详见 12.4）；本 PRD 的产品侧风险项 `R-01` 状态同步更新为"已裁决"。

## 五、核心用户流程

> 规范：每个节点都有明确出口；每条流程均含异常分支；下单主路径操作步数 ≤ 4 步。

### 5.1 流程 A：首次进入 → 登录绑定（US-01）

```
小程序启动
  └→ 检查本地登录态
       ├ 有有效 token ──────────────→ 首页（P-02）
       └ 无 token
            └→ 授权页（P-01）
                 ├ 同意微信授权 ──→ 输入工号 + 姓名后 4 位
                 │      ├ 花名册校验通过 ──→ 绑定成功 → 首页（显示"姓名·园区"）
                 │      ├ 工号不存在 ─────→ 提示"工号无效或已离职" → 停留 P-01，可重输
                 │      ├ 员工已停用 ─────→ 提示"账号已停用" → 停留 P-01，提供联系管理员文案
                 │      └ 网络异常 ───────→ 提示"网络异常，请稍后重试" + 重试按钮 → 停留 P-01
                 ├ 拒绝微信授权 ─────→ 说明"需授权微信信息用于识别员工身份与接收取餐提醒" + 重新授权按钮 → 停留 P-01
                 └ 中途退出 ─────────→ 可随时退出，下次进入重新走本流程（不阻断浏览：游客态可浏览菜单不可下单）
```

**设计要点**：先体验后登录——未登录允许浏览首页菜单（禁用加购并提示"下单前请先完成身份绑定"），降低首访门槛；但"加购/结算"强制绑定（因需扣减个人额度并可追溯）。

### 5.2 流程 B：浏览 → 加购 → 结算 → 提交订单（US-02~US-06、US-09）

**主路径（4 步）**：首页选菜 → 加购 → 结算核对 → 提交并扣款。

```
P-02 首页
 └→ 菜品卡片（点击）→ P-03 详情页
      └→ [加入购物车] → P-04 购物车
           └→ [去结算] → P-05 结算确认页
                └→ [提交订单] → 提交订单接口
                     ├ 扣款成功 ──→ P-06 支付结果页（成功，展示取餐码入口）→ P-08 订单详情
                     ├ 余额不足 ──→ 停留 P-05，提示"余额不足，还差 ¥X"，引导余额充值（P1）或联系管理员
                     ├ 库存不足 ──→ 回滚预占，提示"XX 已售完，请调整数量"，并高亮该菜品行
                     ├ 网络/服务异常 → 停留 P-05，保留全部已填内容（含备注），提供"重试"
                     └ 重复点击 ───→ 幂等返回同一订单号，页面不新增订单
```

**关键规则**

- 库存预占：提交订单时对每个菜品 `UPDATE t_dish_daily SET reserved_qty = reserved_qty + ? WHERE dish_id=? AND biz_date=? AND (limit_qty - sold_qty - reserved_qty) >= ?`，受影响行数为 0 即判定售罄。**全程在单事务内**。
- 幂等：请求携带 `requestId`（客户端生成的 UUID），服务端按 `order.request_id` 唯一索引去重，重复提交返回同一订单。
- 购物车与站点绑定：切换站点会清空购物车，需二次确认（见 US-19）。
- 备注：单条 ≤ 30 字，随订单项保存到 `t_order_item.dish_remark`，后台订单详情与 CSV 均可见。

**购物车异常分支**

| 异常 | 提示文案 | 出口 |
|---|---|---|
| 菜品已下架 | "XX 今日已下架，已从购物车移除" | 移除该行，购物车保留其他 |
| 菜品售罄 | "XX 今日已售完" | 该行数量置 0，可删除 |
| 站点已切换 | "切换供餐点需清空购物车" | 确认清空 / 取消切换 |
| 购物车为空 | 空态插画 + "今日还没有选菜" + [去逛逛今日菜单] | 跳 P-02 |
| 未登录 | "请先完成身份绑定" | 跳 P-01 并带 `redirectTo=P-02` |

### 5.3 流程 C：取餐核销（US-15，档口员）

```
后台核销台（A-05）
 └→ 输入/扫描 6 位取餐码 → [核销] → 服务端校验
      ├ 订单存在 且 状态 = READY（待取餐）
      │    └→ 状态改为 COMPLETED，记录核验人/时间 → 显示菜品与份数（"请出餐：扬州炒饭 ×2"）→ 停留核销台，可继续输入下一单
      ├ 订单存在 但 状态 ≠ READY
      │    ├ = PAID/ACCEPTED → "该订单还未出餐完成，请稍候（当前：待接单/制作中）" → 停留
      │    ├ = COMPLETED → "该订单已于 HH:mm 核销，请勿重复发放" → 停留
      │    └ = CANCELLED/CLOSED → "该订单已取消/已关闭，不可核销" → 停留
      ├ 订单不存在 → "取餐码不存在，请核对后重试" → 清空输入框 → 停留
      └ 网络异常 → "核销失败，请重试"（不改变状态）→ 停留
```

**防重复取餐**：核销为幂等操作——重复提交同一取餐码时订单状态与核验记录均不变，仅返回提示文本。

### 5.4 流程 D：后台接单与履约（US-14、US-15）

```
订单列表（A-03）
 └→ 筛选"待支付/待接单" → [批量接单] 或 行内 [接单]
      ├ 选中订单全部处于 PAID → 批量转 ACCEPTED（制作中），返回成功条数与失败明细
      ├ 含状态非 PAID 的订单 → 拒绝整批提交并提示"其中 N 笔状态已变更，请刷新后重试"（不部分成功，避免误操作）
      └ 网络异常 → 提示"操作失败，请重试"，状态未变更
状态流转按钮规则：
 · PAID → [接单] / [取消退款]
 · ACCEPTED → [制作完成→待取餐] / [取消退款]
 · READY → [核销完成（来自核销台）] / [取消退款]
 · 终态（COMPLETED/CANCELLED/CLOSED/REFUNDED）→ 所有操作按钮置灰
[取消退款] → 二次确认弹窗（需输入原因，选填）→ 余额回冲 + 库存释放 + 写 REFUND 流水 + 写操作日志 → 订单转 CANCELLED
```

**管理员代取消（V1.0 兜底路径）**：员工自助取消为 P1（F-10），V1.0 员工无法自助取消时由管理员在此路径处理，保证"取消/退款路径"闭环不断裂。

### 5.5 流程 E：数据导出（US-16、US-17）

```
统计看板（A-02）或 订单列表（A-03）
 └→ 设置筛选条件（日期区间 + 站点 + 状态）
      └→ [导出 CSV] → 服务端按同一口径执行查询
           ├ 行数 ≤ 50000 → 同步生成并直接下载（<10s）
           ├ 行数 > 50000 → 阻断并提示"当前结果 N 行，超过单次导出上限 50000 行，请缩小日期范围"
           ├ 无数据 → 提示"当前筛选条件下无可导出数据"，不生成空文件
           ├ 生成失败 → 提示"导出失败，请重试或联系管理员"，并记录失败日志
           └ 成功 → 下载 CSV + 写操作日志（导出人/时间/筛选条件/行数）
```

### 5.6 流程 F：员工额度不足（US-06）

```
结算页校验余额 < 应付金额
 └→ 提交按钮禁用 + 展示"余额 ¥X，应付 ¥Y，还差 ¥Z"
      └→ [查看余额明细] → P-10 流水页（查看近期扣款记录）
           └→ [联系餐饮部充值] → 展示管理员联系电话 + 复制按钮（不发起站内工单，工单能力进 V1.1 F-17）
```

### 5.7 流程 G：管理员代预留与核销（V1.1，F-34 / REQ-02）

```
A-18 代预留管理（管理员）
 └→ 选择员工（工号/姓名检索）→ 选择菜品与份数 → [生成预留]
      ├ 员工不存在或已停用 → 提示"该员工不存在或已停用，无法代预留" → 停留 A-18
      ├ 当日菜品已售罄 → 提示"XX 今日已售完" → 停留 A-18
      ├ 成功 → 生成预留码 R+6位，预占库存，写 t_reservation(status=RESERVED)
      │        ⚠️ 此时：不扣额度、不生成员工订单、不写扣款流水
      │        → 展示预留码并提示"请转告员工 X，凭预留码取餐"
      └ 网络异常 → 提示"生成失败，请重试"，不产生预留记录
A-05 核销台（档口员）
 └→ 输入预留码 → [核销]
      ├ 预留有效且员工额度充足 → 核销瞬间扣该员工额度（与普通订单 T7 同事务）
      │    → 生成该员工的正式订单 + DEDUCT 流水 → 状态 RESERVED → COMPLETED
      │    → 显示菜品与份数 → 停留 A-05
      ├ 预留有效但员工额度不足 → 提示"XX 余额不足（差 ¥Z），请先充值或作废预留" → 保留预留记录 → 停留 A-05
      ├ 预留已核销 → 提示"该预留已于 HH:mm 核销" → 停留 A-05（幂等）
      ├ 预留已作废 → 提示"该预留已作废" → 停留 A-05
      └ 预留码不存在 → 提示"预留码不存在" → 清空输入 → 停留 A-05
员工侧：P-07 我的订单 / P-08 订单详情【不展示任何代预留记录】（核销后才出现正式订单）
```

**防扯皮条款（团长裁决 C-03）**：代预留订单**不进入员工订单列表，仅存在于核销台**。验收时须逐条核对：预留创建后员工端 `t_order` 无新增、`subsidy_balance` 未变、`t_payment_txn` 无 DEDUCT 流水。

### 5.8 流程 H：订阅预排与当日确认（V1.2，F-35 / REQ-01）

```
P-16 订阅设置（员工）
 └→ [新建订阅] → 选菜品组合 + 份数 + 每日确认截止时刻 + 生效区间 → [保存]
      ├ 保存成功 → 写入 t_subscription(status=1)
      └ 网络异常 → 提示"保存失败，草稿保留" → 停留 P-16
每日 截单前 2 小时（定时任务）
 └→ 为启用中的订阅生成预排订单 → t_order(source_type=SUBSCRIPTION, status=PENDING_PAY) + 预占库存
      └→ 员工小程序收到"今日预排待确认"（订阅消息，F-11 通道）
员工侧 P-02 首页
 └→ 顶部展示"今日预排待确认"卡片（菜品 + 份数 + 剩余确认时间）
      ├ [一键确认] → 走正常扣款 T2 → status=PAID（与普通订单完全同口径）
      ├ 确认截止时刻到达仍未确认 → 系统定时任务 T11
      │    → 释放预占库存 + 转 SUBSCRIPTION_EXPIRED + 写 yshop_store_order_status 流水(subscription_expired)
      │    → 员工端提示"今日预排已过期，未自动下单"
      └ 网络异常 → 提示"确认失败，请重试"，预排仍保留至截止时刻
```

**红线约束**：预排订单**复用 `t_order`**，因此核销、统计、CSV 导出口径与普通订单完全一致；但**必须**用 `source_type` 区分（否则无法单独核算预排确认率），且预排过期**必须**转独立状态值 `SUBSCRIPTION_EXPIRED` 并写状态流水（否则取餐率与弃单率分母被污染）。

## 七、订单状态机

### 7.1 状态定义

| 状态码 | 中文 | 含义 | 是否终态 | 员工端可见动作 | 后台端可操作 |
|---|---|---|---|---|---|
| PENDING_PAY | 待支付 | 订单已创建、库存已预占，额度未扣减 | 否 | 重试支付（V1.0 内 15 分钟内）、客服联系 | 关闭订单 |
| PAID | 待接单 | 额度扣减成功，等待档口接单 | 否 | 查看取餐码 | 接单 / 取消退款 |
| ACCEPTED | 制作中 | 档口已接单，制作中 | 否 | 查看取餐码 | 标记制作完成 / 取消退款 |
| READY | 待取餐 | 制作完成，等待员工取餐 | 否 | 查看取餐码 | 取消退款（需原因） |
| COMPLETED | 已取餐 | 核销完成，订单闭环 | 是 | 查看详情 | 只读 |
| CANCELLED | 已取消 | 主动取消并已退回额度 | 是 | 查看详情 | 只读 |
| CLOSED | 已关闭 | 超时未支付自动关单，库存释放 | 是 | 查看详情 | 只读 |
| SUBSCRIPTION_EXPIRED | 预排过期 | REQ-01 预排订单在「当日确认截止时刻」未确认，系统自动释放预占库存 | 是 | 查看详情（V1.2） | 只读 |
| REFUNDING | 退款中 | 管理员发起退款处理中（异步退款通道预留） | 否 | 查看详情 | 确认退款完成 |
| REFUNDED | 已退款 | 额度已回冲 | 是 | 查看详情 | 只读 |

> **V1.0 实际启用（7 态）**：PENDING_PAY / PAID / ACCEPTED / READY / COMPLETED / CANCELLED / CLOSED。
> **V1.2 追加（1 态）**：SUBSCRIPTION_EXPIRED（REQ-01 预排过期）。
> **扩展预留（V1.0 不启用）**：REFUNDING / REFUNDED（SUBSIDY_BALANCE 通道同步退款，不产生中间态）。

### 7.3 流转规则表（触发方 / 前置条件 / 副作用 / 非法流转处理）

| # | 起始状态 | 目标状态 | 触发方 | 前置条件 | 副作用（同一事务） | 非法调用处理 |
|---|---|---|---|---|---|---|
| T1 | （无） | PENDING_PAY | 员工 | 已登录、库存足、金额未超限 | 创建订单与明细、生成订单号与取餐码、预占库存、写 request_id 幂等键 | 库存不足 → 回滚并提示售罄 |
| T2 | PENDING_PAY | PAID | 系统（扣款） | 余额 ≥ 应付金额 | 扣减余额、写 DEDUCT 流水、扣减额度累计、写审计 | 余额不足 → 停留 PENDING_PAY，余额不变，可重试 |
| T3 | PENDING_PAY | CLOSED | 系统定时任务（1 分钟粒度） | 超过 15 分钟未支付 | 释放预占库存、订单关闭 | — |
| T4 | PENDING_PAY | CLOSED | 员工（V1.1 F-10）/ 管理员 | — | 释放预占库存 | — |
| T5 | PAID | ACCEPTED | 管理员/档口员 | 订单属于其数据范围 | 记录接单人、接单时间 | 已被他人接单 → 提示"该订单已被接单" |
| T6 | ACCEPTED | READY | 管理员/档口员 | — | 记录出餐时间、触发取餐提醒（F-11） | 状态不符 → 按钮置灰 |
| T7 | READY | COMPLETED | 档口员（核销台） | 取餐码正确且订单属其站点 | 记录核验人、核验时间 | 重复核销 → 返回"已于 HH:mm 核销"，状态不变 |
| T8 | PAID / ACCEPTED / READY | CANCELLED | 管理员 | 填写取消原因 | 额度回冲（REFUND 流水）、释放/回滚库存、写操作日志、通知员工 | 状态为终态 → 按钮置灰 |
| T9 | PAID / ACCEPTED / READY | REFUNDING → REFUNDED | 管理员 | 未来接入异步退款通道时 | 同步退回额度、库存释放、审计留痕 | V1.0 不启用 |
| **T11** | PENDING_PAY（**预排来源**） | **SUBSCRIPTION_EXPIRED** | 系统定时任务（REQ-01，V1.2） | 预排订单到达「当日确认截止时刻」仍未被员工确认 | **释放预占库存**；**必须写一条 `yshop_store_order_status` 流水（建议 `subscription_expired`）**；不扣额度、不产生退款 | 状态为终态 → 按钮置灰 |
| T10 | 任意 | 不可跳级流转 | 任意 | — | — | 服务端返回 409 + 提示"当前状态为 XXX，不支持该操作"，前端按钮置灰 |

> **T11 补充说明**：`SUBSCRIPTION_EXPIRED` 与 `CANCELLED`、`CLOSED` **三者必须为三个独立状态值，不可合并**（团长裁决 C-05 第三条）。运营需据此分别归因「用户反悔（取消）」「超时未付（关闭）」「预排未确认（预排过期）」三类断点。
> **排期提示**：T11 仅在 REQ-01（V1.2）启用；V1.0/V1.1 的预排相关逻辑**不实现**，但**状态枚举值与 `yshop_store_order_status` 流水写入机制需在基座预留**，避免 V1.2 回头改表。

### 7.4 关键不变量与状态机红线（研发须实现的硬约束）

**不变量**

1. **额度不为负**：`UPDATE t_employee SET subsidy_balance = subsidy_balance - ? WHERE id = ? AND subsidy_balance >= ?` 受影响行数必须为 1，否则判定扣款失败。
2. **库存不超卖**：`sold_qty + reserved_qty ≤ limit_qty` 恒成立，由同一行级条件更新保证（`WHERE limit_qty - sold_qty - reserved_qty >= ?`）。
3. **幂等**：`t_order.request_id` 唯一索引；`t_payment_txn.txn_no` 唯一索引；重复提交返回首次结果。
4. **终态不可逆**：COMPLETED / CANCELLED / CLOSED / SUBSCRIPTION_EXPIRED / REFUNDED 不可再流转，仅可由管理员发起"冲正"流程（不在 V1.0 范围，需线下财务调整 + 操作日志）。
5. **金额精度**：所有金额以 `DECIMAL(10,2)` 存储与计算，禁止使用浮点；前端展示与服务端计算结果必须一致（差值 = 0）。
6. **一次核销只发一份餐**：核销接口对同一订单的第二次调用不改变任何状态。
7. **预排过期必留痕**：REQ-01 预排订单转 `SUBSCRIPTION_EXPIRED` 时，**必须**同时写入一条 `yshop_store_order_status` 流水（建议 `subscription_expired`），否则取餐率与弃单率的分母会被污染。

**状态机三条红线（团长裁决 C-05，已同步 fullstack-engineer 与 growth-operator）**

| # | 红线 | 违反后果 |
|---|---|---|
| 🔴 **红线一** | `COMPLETED`（已取餐）**只能由「取餐码核销」写入**，**不得复用 yshop 的「确认收货」动作置终态**。yshop 是电商订单模型、靠收货表达终态；本产品是"取餐即终态" | 员工收了餐但没核销、或核销了状态没动 → **取餐率与北极星指标 WPO 全部算错** |
| 🔴 **红线二** | 「已关闭」（15 分钟超时未支付）与「已取消」必须是**两个独立状态值** | 弃单率（≤3%）与取消率（≤3%）无法分开核算，运营断点归因全部失效 |
| 🔴 **红线三** | **预排过期（`SUBSCRIPTION_EXPIRED`）、已关闭（`CLOSED`）、已取消（`CANCELLED`）三者必须是三个独立状态值，不可合并** | 运营无法分别归因「用户反悔」「超时未付」「预排未确认」三类断点 |

## 九、非功能性需求

### 9.1 性能与容量

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 小程序首页首屏 | P95 ≤ 1.5s（4G/Wi-Fi 混合），P99 ≤ 3s | 真机埋点 `page_view` → 首屏渲染 |
| 菜品详情页 | P95 ≤ 1.2s | 同上 |
| 提交订单接口 | P95 ≤ 800ms，峰值 50 TPS 下 3xx 错误率 < 0.1% | 服务端网关埋点压测 |
| 核销接口 | P95 ≤ 500ms（档口高峰期 20 TPS） | 压测 |
| 后台看板加载 | P95 ≤ 2s（30 天区间） | 压测 |
| 订单列表分页 | 每页 20 条，P95 ≤ 1s | 压测 |
| CSV 导出 5 万行 | ≤ 10s（同步生成） | 压测 |
| 峰值容量假设 | 在册 2000 人，午市 11:00~11:30 内 30% 下单 = 600 单/30min ≈ 0.33 TPS，均值低但存在整点尖峰，按 50 TPS 设计并做 2 倍冗余 | 容量模型 |

### 9.2 可用性与容灾

- 核心下单链路（菜单查询、提交订单、扣款）工作日 10:30~13:30 可用性 ≥ 99.9%，全天 ≥ 99.5%；
- MySQL 8.4 主从复制 + 每日全量备份（保留 30 天）+ binlog 增量实时归档；RPO ≤ 15 分钟，RTO ≤ 2 小时；
- 应用无状态多实例部署，会话令牌存储于共享缓存（Redis 或数据库），支持滚动发布；
- **降级预案**：Redis/缓存不可用时退化为直查数据库（牺牲延迟保可用）；额度扣减服务不可用时暂停下单入口并展示"系统维护中，请稍后重试"，**不得**先创建订单再异步扣款（避免额度透支与订单悬挂）；
- 图片走对象存储 + CDN，菜品图不可用时展示占位图，不阻塞下单。

### 9.3 安全与权限

| 项 | 要求 |
|---|---|
| 后台认证 | 账号 + 密码（bcrypt 加密存储，cost ≥ 10），登录失败 5 次锁定 15 分钟 |
| 后台会话 | Token 有效期 2 小时，超时跳转登录页；敏感操作（余额调整、退款、导出）二次确认 |
| 数据隔离 | CANTEEN_ADMIN 仅见 `site_id = 自身站点` 的订单/员工/菜品；STALL_CLERK 仅见核销相关；越权接口返回 403 且不返回任何业务数据 |
| 员工侧数据 | 员工仅可见本人订单与本人余额；接口层强制按 `emp_id` 过滤，禁止由前端传参决定归属 |
| 接口安全 | 全站 HTTPS；小程序 request 域名单独配置；关键接口签名/防重放；限制非法参数（价格、数量在后端重新计算，不信任前端传入金额） |
| 隐私合规 | 采集清单明示（openid、工号、姓名、部门、手机号）；提供《隐私政策》与《用户协议》页；不采集与订餐无关的通讯录/位置信息（取餐点由员工归属园区确定）；离职员工账号停用并保留历史订单 |
| 审计 | 所有写操作留痕（t_op_log），保留 ≥ 180 天，只增不改不删 |

## 十一、整体验收口径（交付判定）

1. **流程验收**：5.1~5.8 八条核心流程全部端到端跑通，含全部异常分支，异常分支均有明确出口（无"到这一步之后用户去哪"的留白）。其中 5.7 代预留（V1.1）与 5.8 订阅预排（V1.2）随对应版本验收。
2. **功能验收**：18 项 P0 功能的验收标准逐条通过，P0 缺陷数 = 0；P1/P2 未实现不阻塞本期上线。
3. **数据验收**：看板指标与订单列表在同一筛选条件下的订单数完全一致；CSV 在 Excel 打开中文不乱码、金额 2 位小数、日期格式统一；额度流水的 `balance_before/after` 与 `t_employee.subsidy_balance` 可逐笔对平。
4. **压测验收**：50 TPS 下单压测 10 分钟，3xx 错误率 < 0.1%，无超卖、无额度透支；核销接口 20 TPS 下 P95 ≤ 500ms。
5. **权限验收**：三类角色越权访问全部返回 403 且不泄露业务数据。
6. **上线合规**：小程序类目资质、域名备案与 HTTPS、隐私政策页可访问、订阅消息模板已申请。
7. **状态机红线验收（v1.1 新增，团长裁决 C-05，逐条必测）**：
   - 红线一：调用 yshop 原生「确认收货」接口**不能**把订单置为 `COMPLETED`；只有取餐码核销接口能置 `COMPLETED`；
   - 红线二：`CLOSED` 与 `CANCELLED` 在数据库中是**两个不同的 status 值**，且统计接口能分别输出弃单率与取消率；
   - 红线三：`SUBSCRIPTION_EXPIRED` / `CLOSED` / `CANCELLED` **三个互斥状态值**存在，且预排过期时 `yshop_store_order_status` 有对应流水记录（`subscription_expired`）。
8. **券/积分屏蔽验收（C-04）**：小程序端不存在任何券/积分页面路由与 TabBar 项；管理端 CANTEEN_ADMIN 登录后看不到券/积分菜单；直接调用券/积分发放接口被 403 拦截；**数据库中 `yshop_coupon` / `yshop_score_*` 表与种子数据完整未被删除**。
9. **代预留验收（F-34，V1.1）**：创建代预留后——员工余额**未变动**、员工订单列表**无该记录**、`t_payment_txn` **无 DEDUCT 流水**；核销瞬间才扣额度并生成订单与流水；核销记录可在 A-18 与 A-05 查询到。
