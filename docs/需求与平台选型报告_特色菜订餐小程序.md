## 0. 结论先行（TL;DR）

| 项 | 结论 |
|---|---|

### 2.2 MVP 取舍依据（requirement-analysis.md 第二章）

- **闭环优先**：REQ-001~007 构成「顾客下单 → 运营推进 → 运营导出」的完整闭环，MVP 15 个功能点，恰在反清单上限内。
- **单端先行**：仅 C 端小程序 + B 端 Web 后台两端，不做 App / 鸿蒙 / 桌面端。
- **人工替代**：配送调度、客服对账暂用电话/微信群，不自建骑手端。
- **第三方优先**：微信支付、微信登录、订阅消息全部走微信官方能力；导出用后端 CSV 流式生成（不引 POI 之外的重依赖）。

## 3. 平台选型（对照 platform-selection.md）

### 3.1 目标用户设备习惯四步判断法

| 步骤 | 判断 | 结论 |
|---|---|---|
| ① 画用户状态 | C端顾客：午餐/晚餐时段在办公区或门店，手持手机、在微信聊天窗口内；B端运营：办公桌前长时间操作、月末导数据 | C端 → 移动端（微信内）；B端 → 桌面/Web |
| ② 判使用频次 | 订餐为**低频次**（日 1~2 次，但月内集中）；导数据为**周期性低频**（每周/每月） | 低频场景 → **不装 App**，用小程序 + Web 后台 |
| ③ 判人群设备构成 | 集团员工/消费者在微信生态内，接受度最高；含中老年用户 → 微信生态覆盖最好；B端为办公 Windows 机 | C端 → 微信小程序；B端 → 桌面浏览器 |
| ④ 判关键动作 | 需**微信内分享/扫码进入**、**订阅消息触达**、**微信支付**；导出需大表格下载（浏览器天然擅长，App 不便） | 小程序 + Web 后台 完整覆盖 |

**四步判断法结论：C 端主入口 = 微信小程序；B 端管理 = Web 后台。**

### 3.2 七类平台对比矩阵逐维度打分（5分制，分越高越适配）

| 维度 | 网站Web | App(跨端) | 小程序(微信) | iOS原生 | 鸿蒙 | 桌面软件 | 公众号H5 |
|---|---|---|---|---|---|---|---|
| 开发成本（越低越适配=高分） | 4 | 2 | **5** | 1 | 2 | 2 | 5 |
| 获客入口契合（微信扫码/分享/搜一搜） | 2 | 3 | **5** | 2 | 2 | 1 | 3 |
| 能力边界满足（支付/触达/扫码） | 2 | 5 | **4** | 5 | 4 | 2 | 2 |
| 审核与发布成本（越低越适配=高分） | **5**（仅备案） | 2 | 3 | 1 | 3 | 5 | **5** |
| 上手/留存契合（低频轻交互） | 3 | 1 | **5** | 1 | 3 | 2 | 4 |
| 更新灵活性 | **5** | 3 | 3 | 2 | 3 | **5** | **5** |
| **加权总分（权重按本需求调整）** | 3.3 | 2.4 | **4.5** | 1.8 | 2.6 | 2.5 | 4.0 |

**打分说明**：本需求是「低频 + 强微信依赖 + 零 App 装机意愿 + 需低成本持续迭代」，因此「获客入口契合」「上手/留存契合」「审核与发布成本」三项权重上调（各 ×1.5），「能力边界」权重下调（×0.8，本需求无需蓝牙/传感器/长时离线）。

### 3.3 决策树路径

```
开始
 ├─ 需求是否合法合规？ → 是（餐饮订餐，无一票否决项）→ 继续
 ├─ 用户主要在什么设备上产生需求？
 │   ├─ 桌面/长时操作 → 桌面软件 或 Web 应用
 │   │    └─ ✅ 命中：B端运营（总部/门店管理员，办公桌前长时操作 + 月末导数据）
 │   │         → 选 Web 应用（远程协作/多人使用 → Web 优先于桌面软件）
 │   ├─ 线下扫码/微信内传播 → 微信小程序（+ 简易后台）
 │   │    └─ ✅ 命中：C端顾客（微信内下单、扫码进入、订阅消息触达）→ 微信小程序
 │   └─ 移动低频 → 小程序或公众号H5
 │        └─ ✅ 命中：低频订餐，公众号H5 缺支付/订阅消息能力 → 小程序（非 H5）
 ├─ 是否需要 B 端管理后台？ → 几乎总是 → Web 后台（与技术栈同构优先 → Vue3 + Element Plus，与 yshop 底座一致）
 └─ 输出：推荐端组合
```

### 3.4 跨端方案判断（platform-selection.md 第四章）

决策顺序：**预算与团队能力 → 是否需要同时上小程序 → 性能/体验要求 → 生态成熟度**

| 方案 | 优势 | 劣势 | 本项目适配 |
|---|---|---|---|
| 原生（Swift/Kotlin） | 性能/系统能力 | 双端两套代码，成本高 | ❌ 本需求不需要原生能力，且低频场景装 App 会被卸载 |
| Flutter | 双端一致性好 | 包体大，生态非微信原生 | ❌ 不产出小程序，偏离获客入口 |
| React Native | 前端团队复用 | 需原生协助 | ❌ 同上 |
| **uni-app** | 一套代码多端（含微信小程序）、国内生态成熟、**与目标技术栈硬约束一致** | 复杂交互体验上限较低 | ✅ **选定**。本需求交互简单（列表/加购/结算），不触碰 uni-app 能力天花板 |

**跨端结论：uni-app 保留，不引入 Flutter/RN/原生。** 理由：目标技术栈已硬性指定 uni-app；且获客入口决定必须出微信小程序，uni-app 是唯一「一套代码同时满足小程序 + 后台前端语言统一」的方案。

### 3.5 选型结论（唯一主推荐，精确到端形态）

> **推荐端组合（唯一主推荐）**：
> 1. **C 端 = 微信小程序**（uni-app + JavaScript，微信原生容器）：覆盖「特色菜展示 → 购物车 → 下单支付 → 订单状态查询」；获客走微信搜一搜/群分享/扫码；触达走订阅消息。
> 2. **B 端 = Web 后台管理**（Vue 3 + Element Plus + Vite，浏览器访问）：覆盖「菜品/分类/门店管理 → 订单管理与状态推进 → 订单 CSV 导出 → 经营统计看板」。与 C 端同构（同一套 Java/SpringBoot3 + MySQL8.4 后端），**不做 App、不做桌面客户端、不做独立公众号 H5**。
>
> **备选组合（切换条件）**：若集团要求「无需浏览器、门店大屏/打印机直接操作」→ 在 B 端追加 **桌面端收银/POS**（可后置）；若要求「骑手接单」→ 追加**骑手端小程序**（需额外配送资质，见 5.4）。
>
> **各端关键风险**：小程序端 —— 审核 1~7 天、类目资质（餐饮需食品经营许可证）、包体积 2MB/主包 20MB 分阶段、订阅消息需用户逐次授权；Web 后台端 —— 无商店审核，但需 ICP 备案域名 + HTTPS。

## 7. 结论与建议

### 7.1 值不值得做

**值得做，且必须做。** 判断依据：
1. **需求闭环清晰且高频刚需**：订餐是集团内部与客户侧的日常行为，线上化后可直接获得订单数据资产（当前散落在微信群/纸质单，数据不可统计）；
2. **有成熟 MIT 开源底座可省 35~50 人日**，改造后直接对齐集团既定技术栈（SpringBoot3 + Vue3 + uni-app + MySQL8.4），无二次学习成本；
3. **无合规阻断项**：不涉一票否决用途，餐饮类目资质集团大概率已具备；
4. **投入产出**：开发 25~40 人日 + 运行 5,400~13,800 元/年，换取「订单全流程数字化 + 可导出经营数据」，对餐饮集团属高确定性回报。

### 7.2 MVP 范围建议（15 个功能点，封版）

**C 端小程序**：① 特色菜分类列表 + 详情页；② 购物车（加购/改量/删/合计）；③ 结算页（自取/堂食 + 备注 + 联系方式）；④ 提交订单 + 微信支付（未开通则降级「下单后到店付款」）；⑤ 我的订单（按状态分页）；⑥ 订单详情 + 状态时间线；⑦ 微信登录授权
**B 端 Web 后台**：⑧ 菜品/分类/规格管理（含特色菜标签、上下架、改价）；⑨ 订单列表 + 订单详情；⑩ 订单状态推进（制作中/待取餐/完成/取消/退款）；⑪ **订单导出 CSV**（按日期/门店/菜品/状态筛选，UTF-8 BOM）；⑫ 经营看板（今日订单数 / 营业额 / 菜品销量 TOP10 / 时段分布）；⑬ 门店与区域管理（集团多门店）；⑭ 操作员账号与权限；⑮ 微信订阅消息（下单成功通知，可降级）

**明确不做（记录原因）**：骑手端/配送调度（自建配送资质与工期成本高，MVP 用第三方或人工）、桌台扫码（低频场景，后置 V1.1）、用户评价（UGC 审核成本与商店审核风险）、积分/优惠券/储值卡/分销提成（营销系统非本次目标）、多语言（内部用户，中文即可）、KDS 厨房屏（需硬件）。
